# How to draw schemes: rules for the built-in AI

The built-in AI of the editor reads this file when it draws or edits a scheme (builder and assistant):
`lib/ai/settings.php` takes the text between the markers `rule:drawing` and `rule:end`. Do not delete the markers.
Without the closing marker the model would receive the rest of the file. The general skills of the built-in AI are in `deepseek.md`,
the method of interviewing and assembling from the catalog is in `конструктор.md`.
Any agent also reads this file through the link `docs.run&role=draw`. That agent gets one more section, "How to send a scheme to the server",
after the marker `rule:end`.

## Basic principles of a flowchart

Reply to the human in English. Write every block title, description, note text and spec in English.

1. **One block is one action** that one worker can do in one go. Name it with a verb: "Cut out the background".
2. **One entry**: the starter. Every block is reachable from the starter, and every path has an end.
3. **The flow goes by arrows.** Top to bottom. Arrows do not cross without need. Side branches go next to the main path.
4. **A fork is a decision** with two exits, "yes" and "no". For more options, use a chain of decisions.
5. **Work goes in a block, a choice goes in a decision.** A decision does nothing. If a check is needed, put a block before the decision.
6. **A repeat is an explicit loop** with a return arrow and a limit of rounds.
7. **Branches join explicitly.** After a fork from a decision, use `join:"any"`. After parallel branches, use `join:"all"`.
8. **Details go in the spec**, not in the title. The scheme must be readable by titles alone. A big scheme is several folders and gateways.
9. **Keep the block description short.** In the description field give only the general purpose of the block. Write the detailed instruction for the work only in the MD spec. Do not duplicate the spec in the description. The description goes to the worker in the task and counts as **more important than the spec**, so never contradict the spec in it.

## How to draw

**Layout**
- The starter is a circle 160×160 at the top. The first block goes under it. The default block is 280×180.
- The main path goes top to bottom, with about 160 between neighbors. Align by centers, grid step 20.
- Group frame: −40 on the left, −100 on the top (the title is there), +40 on the right and at the bottom.
- Place the inner items first, then the frames. Send all moves in one batch. The server moves nothing by itself.
- Several small schemes are better than one big "zones × lanes" matrix.

**Make every word visible.** Check the layout against these rules before sending:
- **Area label**: it is large (34px, capital letters), placed by height with `valign` (centered by default), and takes a strip of **35% of the width**
  of the area on the `align` side (left by default), over the full height. Put nothing in this strip: no block,
  no decision, no link tag. The content goes in the other 65%, with a 40 margin from the edges.
- The area label is 1–2 short words. The longest word must fit in the strip:
  `area width ≥ (letters in the longest word × 28 + 40) / 0.35`. Otherwise the word breaks in the middle
  ("PREPA-RATION"). For a 280 block in an area, the area width starts from 640, and the label word is up to 6 letters.
- **Group title**: a strip of 100 at the top. Nested items start no higher than `group y + 100`.
- **Link tag**: it is short (“↗ number”) at the card edge at the level of its header (for a decision and a gateway — at mid-height):
  on the right for the owner, on the left for the target; on hover it expands up to 240 sideways.
  This strip must be free. It must not cross a frame edge, an area label, or other cards.
  Put a link between objects in open space or between frames. Do not lead a link to a block inside an area from the side
  of the area label.
- **Arrow labels.** For the branches of a decision, the label "YES/NO" is drawn automatically. Do not set `title` on an arrow with
  `branch`, or you get "YES · yes". The label of a plain arrow is one short word, and only if the arrow
  does not cross a frame edge. The label sits in the middle and would land on a title or an edge.
- **The return arrow of a loop** goes around the blocks on the side (`fromSide`/`toSide` `r`) and runs 20–40 away from them.
  The frame around the loop blocks needs a margin of 160 on the loop side. Otherwise the arrow and its "NO" land on the frame edge.
- Cards must not overlap. Keep at least 40 between neighbors.

**Styling**
- Color (`style.color`) is a named color (`blue`, `green`, `teal`, `purple`, `red`, `orange`, `yellow`,
  `pink`, `cyan`, `lime`, `brown`, `gray`), a pastel `1`–`6`, `#26344a`, or `gradient-…` / `stripe-…`.
- Use color by meaning and keep it quiet. Frames of groups and areas are dark and quiet (`#26344a`, `#20372e`, `#33284a`, `#2b303a`)
  or have no color. Use named colors as accents on blocks (work, check, final). Pastels `1`–`6` look dirty on a dark
  canvas. Use them only if asked.
- Shape (`style.shape`): a block with text gets only `rect` or `rounded`. `circle` is only for the starter.
  `oval` and `hex` cut the corners of the card, while the title, number and MD icon sit in the corners, so the text is cut off.
  Do not give them to blocks. A decision is the type `decision`, not a shape. A gateway draws its own shape, so do not set `shape`.
- Arrow line (`style.route`): empty means a curve, `line` means a straight line that goes around, `line-simple` means a straight line.
  A folder has the same property, and it overrides the arrow.
- `style.z`: lanes and zones are 0, blocks are 1 (the server sets it if you do not).

**All elements**

| Type | Purpose | How |
|---|---|---|
| `block` | worker's work | spec, `agent`, run properties |
| `decision` | fork | `cond`, two exits `yes`/`no` |
| `gateway` | jump to another folder | `target` = folder id |
| `arrow` | transition | `from`, `to`; `branch:"yes"/"no"` from a decision; `back:true` is a loop return |
| `group` | frame, holds its content; can be collapsed | members have `in:[group id]`; `style.collapsed:true` means collapsed |
| `area` | lane or zone under the blocks | the same `in`; `style.align:"left"/"right"` sets the label side, `style.valign:"top"/"middle"/"bottom"` its height |
| `note` | text, explanation on the canvas | `title`, `description`; not part of the run |
| `table` | table on the canvas | `props.table: {"head":["…"],"rows":[{"name":"…","cells":["…"]}]}` |
| `link` | link to a related object | `from` is a block/group/area, `to` is the object (can be in another folder) |

- A frame must cover its content completely. Calculate the frame size from the nested items (margins are above).
- A run does not execute a group or an area. Arrows go only between a block, a decision and a gateway.

**Styling: `style` keys**

| Key | What |
|---|---|
| `x`, `y`, `width`, `height` | place and size (grid 20) |
| `color` | fill color (list above) |
| `shape` | card shape |
| `z` | layer: lanes 0, blocks 1 |
| `route` | arrow line |
| `dash:true`, `width` | for an arrow: dashed line, line thickness |
| `fromSide`, `toSide` | for an arrow: side `t`/`r`/`b`/`l` where it leaves and where it enters |
| `collapsed` | for a group: collapsed |
| `align` | for an area: label on the left or on the right |
| `valign` | for an area: label at the top, in the middle (default) or at the bottom — `top`/`middle`/`bottom` |

**Starter**: a `block` with `props.start:true`. One per folder, no incoming arrows, no executor.
Its spec is the run description for the leader: the goal, what comes in, and what counts as done.

**Decision and Jev**
- Jev decides the decision. It compares the condition with the answer of the block before the decision. If Jev is not sure, the leader decides.
- To make Jev decide reliably: in `cond` write a yes/no question in words ("the photo has a face"). For the block before the
  decision, set `answer`, a sample line with the needed fact (`face: <word>`). The leader does not compute a formula (`a > 5`)
  in a run. Jev reads it as text.
- No `cond`: Jev reads the spec of the decision. Then put one clear criterion in the spec. With a `cond`, the spec of the decision is not read.

**Loop**: an arrow back with `back:true`. The limit of rounds is `max_attempts`. Each node has its own limit.
A loop node without `max_attempts` gets 20. `run.check`, `begin` and this instruction warn about it.

**Join**: `join` is `all` (default), which waits for all direct inputs, or `any`, which waits for any one. After a decision use `any`.
After parallel branches use only `all`: with `any` the block is issued once per branch, with part of the input.

**Gateway**: a `gateway` with `target` = the id of the target folder. It is a jump to another folder.

**Preparing for a new run**: `run.prepare {"folder":N}` removes from the canvas the statuses of the previous
run, the results and covers that the run attached, and the bindings to deleted files. With `"files":1`
(like the button "↺ Reset the scheme for a run") it also cleans the work folder: it clears `service/steps` and moves files
handed in outside `out/` to `out/rN/`. The result files stay in `out/rN/`, the assets in `in/`
are not touched, and the run history is kept. While a run is going, it is refused. `begin` does the preparation itself.
Call it separately only when someone asks to clean the canvas without a run.

**Example of a batch**

```json
{"ops":[
  {"op":"element.create","ref":"n1","folder":12,"type":"block","title":"Take the source file",
   "agent":3,"props":{"answer":"file: <file>"},"style":{"x":120,"y":240}},
  {"op":"element.create","ref":"n2","folder":12,"type":"decision","title":"Good enough?",
   "props":{"cond":"the image is at least 1024 wide"},"style":{"x":140,"y":500}},
  {"op":"element.create","folder":12,"type":"arrow","from":"n1","to":"n2"},
  {"op":"asset.create","kind":"spec","title":"Spec · Take the source file","text":"…",
   "link":{"element":"n1","role":"spec"}}
]}
```

`ref` is a temporary reference inside a batch. The server returns the real `id` and numbers.

## Element spec

The spec is written for a worker who sees neither the canvas nor the neighboring blocks. Keep it short, two paragraphs:

1. **What to do it with.** The tool, the model, the parameters word for word, the full prompt. Input files come from `in/`
   ("in/photo.png") or from the answer of the previous block ("file from the input").
2. **What to hand in.** The file name in `out/`, the limits, the sign that it is done.

The server adds to the task by itself: the work folder, the block description, the attached assets, the answers of previous
blocks, the `paid_calls` limit, the run spend, the answer sample and the task address ("137.3:"). Do not write them in the spec.
The "Input" gets the answers only of those blocks that have an arrow going to the block (through decisions). If you need
data of a block higher in the scheme, draw an arrow from it. The block sees the run files anyway.

**Answer sample** `answer`: the line to answer with (`file: <file>`, `a=<number> s=<number>`,
`face: <word>`). Placeholders are only `<number>`, `<word>` (no spaces), `<file>` (a path), `<text>`. Everything else is
compared word for word. The server does not reject an answer, but on a mismatch it writes "⚠" to the leader.
For a block with `paid_calls`, the sample contains `calls=<number>`. Write it in one line, without quotes and line breaks.

| Property | Meaning |
|---|---|
| `start` | run starter |
| `answer` | sample of the worker's answer line |
| `cond` | for a decision: the condition for Jev |
| `join` | `all` or `any` |
| `max_attempts` | limit of issues of the block (loop rounds) |
| `outputs` | names of result files. The server uses them to label the files it catches. It does not check that they exist |
| `paid_calls` | limit of paid calls. It is written to the worker in the task. The server does not count it |
| `timeout` | hint for how long to wait for the worker. The server does not track the deadline |

## How to send a scheme to the server

This section is for an agent that got the link `docs.run&role=draw` (the built-in AI does not read it).
The API address, the project key and the folder are in the answer of that link.

**Read.** The whole scheme is `op=folder.get&folder=N`. Every element has `id`, `no`, `type`, `title`,
`description`, `props`, `style`, arrows have `from`/`to`, and `assets` holds the specs (`role: spec`, the `asset` number).
The spec text is `op=asset.get&asset=ID`. A short text outline is `op=scheme&folder=N`.

**Write** in one batch, `POST` with JSON:

```bash
curl -sS -X POST 'API?project=KEY' -H 'Content-Type: application/json' --data @batch.json
```

```json
{"ops":[
  {"op":"element.create","ref":"s","folder":12,"type":"block","title":"Start","props":{"start":true},
   "style":{"x":180,"y":0,"width":160,"height":160,"shape":"circle"}},
  {"op":"element.create","ref":"b1","folder":12,"type":"block","title":"Take the source file","style":{"x":120,"y":320}},
  {"op":"element.create","folder":12,"type":"arrow","from":"s","to":"b1"},
  {"op":"asset.create","kind":"spec","title":"Spec · Take the source file","text":"…","link":{"element":"b1","role":"spec"}},
  {"op":"element.update","id":15775,"title":"New name","style":{"x":400}},
  {"op":"asset.update","id":6096,"text":"new spec text"},
  {"op":"element.delete","id":15790}
]}
```

| Operation | What | Main fields |
|---|---|---|
| `element.create` | new element | `folder` is required; `type`, `title`, `description`, `props`, `style`, `agent`, `in`; for an arrow `from`, `to`, `branch`, `back` |
| `element.update` | edit | `id` from `folder.get` + only the fields that change |
| `element.delete` | delete | `id`; the arrows of a deleted block go with it |
| `asset.create` | block spec | `kind:"spec"`, `title`, `text` (Markdown), `link:{"element":…,"role":"spec"}` |
| `asset.update` | rewrite a spec | asset `id`, `text` |

- `ref` is a temporary name of a new element. `from`, `to`, `in` and `link.element` in the same batch refer to it.
  The answer has the real `id` and `no`: `{"ok":true,"rev":…,"results":[…]}`.
- `style` and `props` in `element.update` are edited key by key: the keys you send are replaced, and `null` deletes a key.
- A batch passes completely or not at all. On an error (`{"ok":false,"error":…}`) nothing is written.
  Fix it and send again.
- While a run is going in the folder, you must not change the meaning of the scheme (`active_run`). Change only the styling (`style`).
  Only a human can stop a run.
- The number `no` is for humans on the canvas. `element.update` and `element.delete` need the `id`.

- `run.prepare` (section "Preparing for a new run" above) is a separate request and does not go in a batch:
  `curl -sS -X POST 'API?op=run.prepare&project=KEY' -H 'Content-Type: application/json' --data '{"folder":N,"files":1}'`
