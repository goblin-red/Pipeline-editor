# Run — instructions for the leader and the worker

Texts of the run instructions. The server builds from them an instruction for a folder (`lib/api/instructions.php`):
the team setup (solo or team) and the environment (subagents, Orca, SendMessage). Each part goes from its own mark
`<!-- part:имя -->` to the next one; the line break before a mark is a separator, not text.

Substitutions: `{{имя}}` — inserted by the server at build time (another part or a value); `{G}`, `{KEY}`,
`{FOLDER}`, `{WATCH}`, `{HERE}`, `{RUN}` — API address, project key, folder, watchdog, the leader's own folder (web), run number.
This is the English version; the Russian one is instructions/ru/прогон.md: same marks and substitutions.

## Rules

- **You do every block yourself:** `task` → read the task at the link → do it → `done` with your own answer.
  How to do it — the section “How to do a block”.
- **Do not call subagents or other agents** — even for heavy blocks.
- **Do not open generated images** to look at them — only if the spec directly requires it.
  The file path is enough: big images in a request can hang you.
- **Submit a finished block at once** (`done`), do not wait for the other parallel ones: if something fails, what was
  submitted is already saved.
- **Nobody checks the substance of the work** — neither the server, nor the human along the way; the server only compares the form
  of the answer with the pattern and writes “⚠”. Answer “done” only when it is truly done.
- Do not edit the scheme or the spec. If something is wrong — tell the human and wait.

Call the human and wait if the trouble is in the scheme itself (`SCHEME NOT READY`, no spec, attempts ran out),
a block fails a second time, or the run must be closed (`op=stop` — only on the human's word).

**1. You are a courier, not an editor.**
- Pass the task to the worker exactly as the server gave it: the line “task at link …” — whole. The worker reads it, not you.
  The worker reads the file, not you.
- Pass the worker's answer to the server **verbatim**: do not edit, add to, or round it.
{{self}}

  until all its inputs are accepted, and if something fails, what was submitted is already saved.
- **Nobody checks the substance of the work** — neither you, nor the server. If the worker said “done”, you believe
  it. The server checks the round address, and softly the form of the answer against the pattern (“⚠”, the answer is accepted anyway).
- Do not edit the scheme or the spec. If something is wrong — tell the human and wait.

**2. You are the safety net of the run.** The server drives the run: it issues blocks, Jev decides decisions. If the run
goes off track — you sort it out, yourself and in time:

| What went wrong | What you do |
|---|---|
| Jev did not decide a decision | you choose the branch yourself by the condition and the answer (section “Decisions”) |
| the worker is silent (watchdog: `SILENCE`) | ask the worker; if silent a second time — call the human (section “Watchdog”) |
| the worker sent `ERROR: task N.K — …` | this is not an answer, it does not go into `done`. Block not accepted — let the worker redo it and answer again; already accepted — `op=again&block=N` and give the task to the worker again |
| a block is `STUCK` because of a worker failure | `op=again&block=N`, once |

Call the human and wait if the trouble is in the scheme itself (`SCHEME NOT READY`, no spec, attempts ran out),
the same block failed a second time, or the run must be closed (`op=stop` — only on the human's word).
The safety net covers decisions **about the run**, not about the work.

## How to do a block

{{intro}}At the top of the task are service lines; below them is the block spec, as the human wrote it:

| Line | What is in it |
|---|---|
| `Block 43 “…” · task 43.2` | the block and the task address: block 43, round 2 |
| `Round 2 — decision 44 “…” sent it back: branch no …` | the block is done again in a cycle; in “Input” the answers are fresh, lines “(previous input)” are from the previous round |
| `Work folder: …` | all paths in the task are from it; run commands from it |
| `Materials — in/. Put results in out/rN/ …` | `in/` — the human's materials, read only. `out/rN/` — the results of this run: whatever the spec and “Input” call `out/…` is this folder |
| `Block assets (read before you start): …` | files attached to the block — read them before the work |
| `Run files (already made): …` | what the run has already put in `out/rN/` — for understanding; take numbers and answers from “Input” |
| `Description (overrides the spec; …): …` | a short description from the human; if it differs from the spec — do it by the description |
| `Scheme overview (for context, not a task): link` | the frame of the scheme, if the human turned it on; read it with `curl -s` once; for understanding, not a task |
| `Input:` and below `block 42 “…” → …` | answers of previous blocks verbatim: take numbers and files only from here |
| `Paid calls at most: 3` | the limit for paid services — do not exceed it |
| `Paid calls in this run so far: 3` | how many paid calls the run has already spent — for final blocks |
| `Answer in one line like: 43.2: …` | the answer pattern — starts with the address |

- The answer is **one line by the pattern**, address first: pattern `137.3: a=<number> b=<number>` →
  answer `137.3: a=11 b=1`. Copy the address from the pattern, replace `{name}` with the value.
- One task — one answer. Do not do the next round in advance, do not count ahead.
- If you noticed something important (a file is missing, data looks strange) — put a note in the same line before the address:
  `Note: DSC09524.JPG is missing — 76.4: a=4`. The server will write it to the log.
- Create files only if the task directly asks; name the path of the finished file in the answer.
- Do not touch folders of past runs (`out/r8/` and older) or `in/`.
- If you cannot — do not guess: `op=fail&block=N&why=…` and tell the human.

## Watchdog — a safety net if everything stops

This is **not a working round**. {{why}}
Start it as a **background command** right after `begin` (in Claude Code — Bash with `run_in_background`):

```bash
{WATCH} {KEY} r109
```

**Do not start the watchdog with `&` and output to a file**: its line will go to the file, and it will wake
no one. The background command must itself return the watchdog output to you when it finishes.
One watchdog per run. You do not need to remove it: after the run ends it finishes itself with the line
`RUN CLOSED`. If your environment does not wake you when a background command ends (as in Codex), do not
start the watchdog — it would wake no one; keep the loop going without distractions.

| Watchdog line | What to do |
|---|---|
| `RUN CLOSED: …` | nothing — the run passed or was stopped |
{{rows}}| `SILENCE: … block N … — you do it yourself` | the block is yours: submit it (`done`), if it fails — `fail` and tell the human; start the watchdog again |
| `SILENCE` — it is up to you (your block, a decision, “STUCK”) | do what `op=where` says and start the watchdog again |
| `NO STATUS: …` | the server does not answer or there is no run — tell the human |

## Worker link · environment “Subagents”

Workers are your subagents: in Claude Code — the `Agent` tool, in other CLIs — their way of starting
subagents. There are no separate terminals. The environment was chosen by the human — this is permission to start
subagents in this run; do not ask again.

**You decide who does a block:** hand it to a subagent or do it yourself (section “How to do a
block”). Agent cards on blocks do not apply here.

**You also decide how many subagents:** a new one for each task (each has a clean slate) or
one for the whole run, if your CLI can continue the same subagent (in Claude Code —
`SendMessage` by its name or id): you send the next tasks to it with the line “task at link …”.

**The first message to a subagent** — two lines: the briefing and the task line.

```text
<reply to curl -s "$G&op=invite&run=rN">
task at link …
```

Take the briefing from the server once and give it to every new subagent verbatim — do not rewrite or
add to it. If the server opened several blocks at once — you can start one subagent per block.

**The answer** is the subagent's final message; into `done` goes all of it, verbatim. The subagent
does not lead the run and does not go to the Goblin server.

## Worker link · environment “SendMessage”

The leader and the worker are separate Claude Code sessions on one machine. Messages go through the built-in
Claude tools: `ListAgents` — who is there, `SendMessage` — send. A message is **one
line**. Blocks with a worker on the card are done by the worker session; a block marked `do it yourself` — by you.

**Find the worker yourself.** Call `ListAgents`: it shows the other Claude sessions on this machine.
The worker is the session the human opened for the run. Its name may be given in the task link
(`&worker=…`); if not — look for a session with the word “worker” in its name. If you did not find one or several fit —
ask the human. Write the name exactly as `ListAgents` printed it.

**The worker briefing** is the first message to it, right after `begin` and the watchdog. The server gives the text:

```bash
curl -s "$G&op=invite&run=rN"
```

Send it **verbatim**: `SendMessage` with `to` — the worker name, `message` — the server reply. Then —
the first task.

**The task** — `SendMessage` to the worker with the line “task at link …”.

**The worker's answer** will come to you as an incoming message from its session. When you see a notification of new
messages — read them (`ReadNotifications`). Into `done` — the whole answer, verbatim.

**Do not send the same thing twice:** `SendMessage` delivers by itself. No answer — wait for the watchdog, it will say
when to ask the worker.

## Communication · environment “Orca”

The leader and the worker sit in separate Orca terminals. Messages go through the command `orca terminal send`.
A message is always **one line with no line breaks**.

**Waiting for an answer — end your turn.** After you send a message, say “waiting” and stop: wait at the
input line. Do not wait inside the turn — with the `sleep` command, terminal polling, or a loop: the message
will arrive, but Orca will not see the turn start, and every send will drag on through retries.

**Receipt.** `--wait-submit 4` waits up to 4 s for the receiver to start a turn with your message. Do not
wait longer. Read the Orca reply as a digest through `jq`, as in the examples below: `stages`, `requestId`,
`provider`, `observation`, `warnings`. Do not cut it with `grep`, `head`, `tail`: that loses
`requestId`, and without it a receipt retry is impossible. If you lost `requestId`, do not
send again blindly: end your turn and wait.

A warning “input was accepted but no turn start was observed” means the text is already in the
receiver's terminal. Usually the receiver is just busy, but Enter may have been lost. Repeat the same command **once** with
`--retry-request <requestId from the receipt> --wait-submit 4`: this is not a second copy, it is the same receipt
again.

**The send answers `agent_prompt_blocked`** — the receiver has a window of the CLI itself open (model menu,
limit reminder, question). Do not close it yourself and do not send keys to another terminal: tell
the human “a CLI window is open in the terminal — close it” and wait. Then repeat the send with
`--retry-request <requestId> --wait-submit 4`.

<!-- part:lead_orca -->
**Who does what.** Blocks with a worker on the card are done by the worker in its terminal; a block marked
`do it yourself` is yours.

**Your own address** is in the variable `$ORCA_TERMINAL_HANDLE`. Get it with a separate command
`printenv ORCA_TERMINAL_HANDLE` (on macOS `printenv` with several names checks only the first).

**Where the worker is.** It is given in the task link as `&worker=term_…` — use that exact address. If it is not
given, the instruction to conduct the run allows you to create the worker in Orca yourself. After `begin`
and the watchdog:

1. Call `project.get` with the project key. By the worker id from `docs.run`, find its card in
   `agents`: `cli`, `model`, `effort` are its, not yours. No `model` or `effort` — start the CLI without
   those flags. No card — use the same CLI as yours.
2. Read the skill `orca-cli`. Through `orca terminal show --terminal YOUR_HANDLE --json` get your own
   `worktreeId`; do not derive it from the current directory.
3. Create the worker: `orca terminal create --worktree id:WORKTREE_ID --title "rN worker"
   --command 'CLI_COMMAND' --json` in this same worktree. Start the CLI in the Goblin root. For Codex
   the command looks like `codex -C GOBLIN_ROOT --model MODEL -c 'model_reasoning_effort="EFFORT"'`.
4. Save `terminal.handle` from the reply. Do not invent an address and do not look for the worker by a similar name.
   If the creation turned out ambiguous — find out the result through Orca before creating again.
5. Wait for `orca terminal wait --terminal HANDLE --for tui-idle --timeout-ms 60000 --json`:
   only `satisfied: true` allows sending the intro.

After the run, if the card has `closeAfter=keep`, leave the terminal open; if `closeAfter=close`,
close only the worker you created, after the last answer is accepted.

**The worker intro** is the first message, in one command:

```bash
orca terminal send --terminal WORKER_TERMINAL \
  --text "$(curl -s "$G&op=invite&run=rN&reply=$ORCA_TERMINAL_HANDLE")" --enter --wait-submit 4 --json \
  | jq -c '{ok, error, stages: .result.send.prompt.stages, requestId: .result.send.prompt.requestId, provider: .result.send.prompt.provider, observation: .result.send.prompt.observation, warnings: .result.warnings}'
```

**Task:**

```bash
orca terminal send --terminal WORKER_TERMINAL --text "task at link …" --enter --wait-submit 4 --json \
  | jq -c '{ok, error, stages: .result.send.prompt.stages, requestId: .result.send.prompt.requestId, provider: .result.send.prompt.provider, observation: .result.send.prompt.observation, warnings: .result.warnings}'
```

**The answer** comes as the message `WORKER ANSWER: 137.3: a=11 b=1`. In `done` put everything after
`WORKER ANSWER: `, word for word (the server also understands the prefix).

Do not read the worker's screen and do not check before sending whether it is free: for a busy worker the message waits in
the queue. After sending, end your turn and wait for `WORKER ANSWER`. If the warning appears again after the receipt retry,
do **not** send the task again: wait for the answer; if it does not come, the watchdog will tell you.

## Server replies — what to do

| Reply | What to do |
|---|---|
| `ok: block 137 accepted · task 137.3 · answer “…”` | go on around the round; in the quotes is exactly what you sent |
{{note}}| `decision 138 → no · Jev: no 1.00` | nothing, for information |
| `⚠ answer does not match the pattern “…”` / `⚠ arithmetic does not match the input` | the answer was accepted, but it is wrong. It is an error — redo it: `op=again&block=N`; the server removes the unclaimed issue and the decision after it itself; that is by design — go on |
| `⚠ paid calls K with a limit of N` | go on around the round; tell the human |
| `ok: block 137 will be done again · also removed: 138.1 (decision)` | go on around the round: the block is issued again |
| `━━ GATEWAY: block N “…”` | mark the passage: `op=done&block=N` |

## How to answer

Exactly by the pattern, with no extra words. **At the start is the task address with a colon**, as in the pattern.

```
pattern: 137.3: a=<number> b=<number>
your answer: 137.3: a=11 b=1
```

Do not invent or change the address — copy it from the pattern: the server uses it to understand which round you
answered. Replace each placeholder in the pattern — `<number>`, `<word>`, `<file>`, `<text>` and `{name}` — with its value; do not keep the brackets.

## Rules

- **Run commands from the work folder** — first `cd` into it: the paths in the task are relative to it.
- **The block description overrides the spec.** If they say different things — follow the description.
- **Take numbers and files only from “Input”.** Do not invent and do not calculate ahead.
- **One task — one answer, and you send it once.** Do not do the next round in advance.
  If the leader asks you to repeat, send **the same** answer again; the server recognizes a repeat by the address.
  If after sending you realize the answer is wrong **in substance**, send one line:
  `ERROR: task 137.3 — what is wrong`.
- **The answer is one line, and it is the last one.** Explanations, if needed, go in the line above; where a message
  is a single line with no line breaks (Orca), put them as a note before the address.
- **Several tasks came** — answer each as soon as it is ready.
- **You noticed something important** (a file is missing, the data is strange) — put a note **before the address** in the same line:
  `Note: DSC09524.JPG is missing — 76.4: a=4`. The server writes it to the run log.
- **Results go only to `out/{RUN}/`.** `out/x` in the spec means `out/{RUN}/x`: that is by design, no note
  is needed. Do not touch the folders of previous runs or `in/`.
- **Create files** only if the task directly asks for it; name the path to the finished file in the answer.
- **Do not open generated images** to look at them — only if the spec directly requires it.
- **If you cannot do it — say so directly** to the leader and name what is missing. Do not guess.
- **Nobody checks the work**: answer “done” only when it is truly done. If you look at the previous
  block's work and the input is unfit: ask the leader, or decide yourself and say so in a line above the answer.

more than once.
