## 25.09.2026 — analysis of the r34 run hang (compared with r35)

**What happened.** Project `g9x9jenvvr`, folder 10793 "test2": an empty `index.html` → texts and three
images (blocks 182–184) in parallel → assembly of `index.html` (block 180, `join = all`). In both runs
the leader was Codex (gpt-6-sol, medium), "Leader does everything itself"; the task texts of r34 and r35 match
word for word. r34 (18:16–18:26) hung on the images and was stopped by the human; r35 (18:31–18:41)
passed, 7 acceptances. The Goblin server worked without errors in both runs.

**Cause (logs `~/.codex/sessions/…/rollout-…-01a0d922….jsonl` and `~/.codex/logs_2.sqlite`).**
1. The r34 leader generated three images in parallel (ready by 18:19:18), and then decided to
   **look at them** itself: an attempt with `detail=low` is not supported, and the retry with `high` sent the model
   8.7 MB — three PNGs of ~1254×1254 in base64.
2. The connection to `chatgpt.com` was bad from 18:19 to 18:45 in all Codex sessions (timeouts of
   `rateLimits/read`, `models refresh`).
3. The heavy request hung for 5 minutes without a reply → `Broken pipe`, retry 1/5 (18:24:40), reconnection
   and resending of the same 8.7 MB; after 1.5 minutes the turn was interrupted manually.
r35 hit the same disconnect (18:37:42, `websocket closed by server`), but its request was light
(~40 thousand tokens, it did not open the images, only copied a file) — the retry went through unnoticed.

**Remarks.**
- The watchdog fired on time (18:22 "SILENCE"), but there was nobody to wake: the leader was hanging inside a request to
  the model. The watchdog helps when a worker is silent, not when the leader itself hangs.
- With "Leader does everything itself" nobody watches the leader — the run stands still silently, and only the human will notice.
- The text "SILENCE … block 182 in progress" suggests a silent worker, although the executor is the leader itself.
- The finished images were not handed in right away — the leader waited for all three. Had it handed them in one by one, 2 of 3
  would have survived the hang.
- The run did not have to be stopped: the r34 images are intact in `~/.codex/generated_images/01a0d922…/`;
  it would have been enough to interrupt Codex and say "continue r34" (`where` will show the open blocks).
- In r35 the watchdog was started via `&` with output to `/tmp/…log` — in case of silence it would not have
  woken anyone.

**Already done on 25.09.2026:** in the leader and worker instructions (since 26.09 — `lib/api/instructions.php`) — do not open generated images
unless the spec requires it; hand in a finished block right away, without waiting for the parallel ones; in the leader instruction — a ban on
starting the watchdog via `&` with output to a file.

**To do later.**

  interrupt it and tell it to continue, do not stop the run.
- ~~Watchdog (`bin/lead-watch.sh`, the `where&short=1` line in `simple.php`): if the leader itself is doing the block —
  write "SILENCE: block N — you do it yourself — submit it or tell the human".~~ Done 28.09.2026: `goBrief()`
  marks the leader's block "— you do it yourself" (by `goSelf()`), and the leader instruction has a watchdog line.

  based on the time of the leader's last call in the feed. The browser only reads meanwhile.

## Worker greeting before the reply address

**What happens.** Agents have the human's top-level rules — start every reply with a form of address:
Codex writes "Cиньер,", Claude — "Амиго,", Grok — "Глубокоуважаемый, готово!". The worker instruction
does not override this rule, so the last line of a reply can look like this:
`Cиньер, 11.1: a=10 b=0`. Noticed in the run environment tests on 22.09.2026.

**What happens now.** `done` finds the address `N.K:` anywhere in the line (`goAnswerAddress()`,
`lib/api/simple.php`). All text before the address is treated as a **worker remark**: it is written to the log
as the event "замечание worker N.K: …". So the greeting will end up in the log as a false remark.
For now the leader saves the day: in the tests it cut off the greeting itself and passed `done` the line starting from the address.

**What to do.** Teach the server to tell a greeting from a remark and silently discard the greeting.
Greetings differ between agents and people, so a word list will not do. Options for the rule:
- a remark is only text with a colon or one starting with the word "Note"; anything else that is short
  (up to 3–4 words) is a greeting;
- or the worker puts the remark in an explicit frame (`[замечание: …]`), and the server discards everything
  else before the address.

Choose the rule, fix `goAnswerAddress()`, the worker instruction (`lib/api/instructions.php`) (how to write a remark),
`md_backend/ru/progon.md` (the section about the worker remark) and the check in `tests/v2/check-simple.mjs`.

**Decision 28.09.2026:** leave as is for now — monitoring.

## The `goblin` utility — rework for high-load runs

**Current state.** All runs go the simple way: the leader is an agent (Claude, Grok, Codex), sends `curl` to
`api.php`, the worker does not go to the server (the leader instruction (`lib/api/instructions.php`), `worker.md`). The `bin/goblin` utility
(`lib/cli/`, about 3.7 thousand lines, instructions `instructions/old/`) has been taken out of service: the last run
through it was on 21.09.2026. Verified on 22.09.2026: 10 runs the simple way on three CLIs and in three environments —
no server failures.

**Why it may be needed.** When there are many runs or the schemes are big, an AI leader-"postman" is
expensive and slow: it spends tokens on forwarding lines. `goblin drive` drives a run with a script, without AI, and
can drive many runs at once (`tests/v2/check-parallel-live.mjs` — three runs in parallel).
Workers stay agents — the utility replaces only the leader. It also has what the simple
way lacks: server-side checking of hand-ins (`accept`/`reject`, files) and accounting of paid calls (`step.job`).

**What to do.** Rework the utility for the new design rather than fix the old one:
- drive a run by the same rules as the simple way: a task as a file, the round address `N.K`, the description
  outranks the spec, block assets, `in/` and `out/rN/`, run environments (Orca, SendMessage, subagents);
- send tasks to workers and collect answers without an AI leader; decisions — Jev, a failure — to the human;
- decide whether server-side hand-in checking and paid-call accounting are needed, and if so — make them common to
  both ways;
- until then — do not develop or fix the old utility; do not delete `bin/goblin`, `lib/cli/`, `instructions/old/`
  (`readme.md`).

**Decision 28.09.2026:** monitoring.

## Service files on cards

**Status:** monitoring, the decision is the human's (29.09.2026 — "describe in detail in the plans for the future").

**Current state.** `done` attaches to the block every file that the worker named in the reply and that the step created
or changed after being issued (`goCatchFiles()`, `lib/api/simple.php`). The file becomes a step result
(`asset_links`, role `result`) and is visible in the block's assets. Only the first image becomes the cover.
The server does not distinguish a real result from intermediate data, so everything lands on the card.

**Where it is seen.** test_http, runs r6, r19, r26: the blocks "Курс валют" and "Погода" save the raw responses
of the services `rates.json` and `weather.json`. The server replies "на карточке: out/r26/rates.json" and attaches them
on a par with images. These files are data for the next block ("Сводка"), not what the human wants to
see on the scheme. The real result of the chain is `report.md` of "Сводка".

**How it gets in the way.** Nothing breaks. But the block's assets get cluttered: the human opens a card and sees
a service JSON instead of the work. In schemes with many service requests (API, parsing, batches)
there will be many such files, and the real result gets lost among them.

**Options.**

1. **Leave as is.** Do not touch the code. Downside — cards get cluttered as schemes grow.
2. **Do not attach JSON to the card** (recommended). One check in `goCatchFiles()`: a file with the extension
   `.json` is written to the step log (the event "файл 131.1: …" stays), but does not go to `asset_links`.
   Images, video, `.md`, `.txt`, `.html` are attached as before. Pros: one line, the scheme author has nothing
   to fill in, covers the whole observed case. Downside: if JSON is the block's result
   (for example, an export for the human), it will not be on the card — only in the log and in `out/rN/`.
   A rule by file kind (`fileKindOf()`) does not work: `.html` and `.json` are both "code" there, while `index.html`
   in test_mix is a real result.
3. **Attach only what is listed in `outputs`.** If a block has the `outputs` property, only files with those names
   go to the card, the rest — only to the log. Without `outputs` — as now. Pro — exact control
   for the scheme author. Downsides: `outputs` currently means something else — these are slot names that
   `goCatchFiles()` hands to files in order, not file names. The meaning of the property would have to change.
   Every block must be filled in by hand, and the built-in AI must learn to do it.

**What the fix touches (option 2).** `goCatchFiles()` — skipping `.json` before `assetLink`, the path in the `done`
reply ("на карточке: …") without JSON; a line in `md_backend/ru/progon.md` (section "Files on the card") and in the
documentation article "Task, inputs and result"; a check in `tests/v2/check-simple.mjs`, section 5
"Files from the answer": JSON from the reply did not land on the card, the image did.

## Security — audit of 29.09.2026

The project is in the testing stage: security is a separate stage at the end, in about a month (the human's
decision of 29.09.2026). Everything below is confirmed in the code by the audit of 29.09. Already done: scripts in
`public/workfiles/` are not executed and not served (`.htaccess`, `FilesMatch` case-insensitive:
`.php`, `.PHP`, `.phtml`, `.Php5` → 403).

### B1. A guest in an open project equals the owner — high
- **What.** `requireWrite()` (`lib/access/rights.php`) lets anyone write if the project has
  `guest_write = 1`, even when the project has an owner. Right now `guest_write = 1` on all projects, and
  a project is created with any key.
- **Scenario.** An outsider with a project key: `project.delete` — the project is deleted; `token.create` and
  `agent.token` — permanent tokens; `project.update guestWrite=0` — writing is closed to everyone except the
  token issued to themselves.
- **How to close.** For `project.update/delete`, `token.*`, `agent.token`, `folder.transfer`,
  `template.save/delete` require the owner or a project token (`requireOwner`), leave the guest scheme
  editing. Turn off open writing for new projects by default.

### B2. File boundaries are per installation, not per project — high
- **What.** `pathInsideRoots()` (`lib/core/config.php`) checks only the installation roots (`file_roots`).
- **Scenarios.**
  - `folder.update workDir=<root of public/workfiles>`: `asset.workfile` reads the `service/` of other
    projects, rename and delete change their files, `run.prepare` cleans another's `service/steps`.
  - `path=SERVICE/tasks`: the `service/` ban is bypassed by letter case (`realpath` on macOS does not change case).
  - `asset.create uri=<any file in the roots>` (`lib/assets/assets.php`), then `asset.file` serves it.
- **How to close.** The path — only inside the `work_dir` of this project's folders; cut off the `service` segment
  case-insensitively; compare the `realpath` of both paths.

### B3. Tokens do not expire and live forever — high
- **What.** A run token (`gbr_`) is revoked in `runFinish`, `runAttach` and at the end of a turn, but not on
  `run.stop` and not in the turn-stop branch (`lib/engine/advance.php`). On 29.09 the database has 30 live `gbr_`
  for stopped runs. There is no expiry for them or for the 48 agent tokens (`gba_`).
- **Scenario.** A leaked token of the leader of a stopped run writes to the whole project
  (`rights.php`: a project token grants write).
- **How to close.** `tokenRevokeFor('run_id')` in `runStop` and in the turn stop; an expiry on all
  tokens (`expires_at`), extended on use.

### B4. The timeline serves another run — medium
- **What.** `runAsked()` (`lib/engine/runs.php`) accepts a numeric `run=` without checking the project;
  `runTimeline()` (`lib/engine/timeline.php`) does not call `runRow()`; `runForFolder()` — without a project.
- **Scenario.** With access to project A: `run.timeline&run=<run B id>` or `&folder=<folder B>` —
  the response has the steps, block titles and notes of project B.
- **How to close.** In `runAsked` check the numeric id against the project; in timeline — `runRow()` and `folderRow()`.

### B5. Writing from any site — medium
- **What.** `Access-Control-Allow-Origin: *` (`lib/api/http.php`) and parsing a `text/plain` body as JSON.
- **Scenario.** Someone else's page open in the browser sends a POST to `localhost/goblin/api.php` —
  with the user's session cookie.
- **How to close.** CORS only for reading or for its own origin; modifying operations — only
  `application/json` and an Origin check.

### B6. The worker sees too much — medium
- **What.** `assetGet()` (`lib/assets/assets.php`) does not call `fileAllowed()`: an agent token reads the texts
  of all project assets, although `asset.file` restricts this. `asset.workfiles` lists the whole
  work folder, including `service/`.
- **How to close.** The same `fileAllowed()` check in `assetGet`; remove `service/` from the listing.

### B7. Login without limits and a dead admin role — low
- **What.** `userLogin` (`lib/access/users.php`) and `adminLogin` (`lib/access/admin.php`) have no limit
  on attempts and no delay. The `admin` role is unreachable in the API: `caller()` does not read the `goblin_admin` cookie,
  the admin token secret is issued nowhere — the `config.list` branches and the admin deletion of a template are dead.
- **How to close.** A limit on attempts by IP and login; either connect the `admin` role via `caller()`,
  or remove the dead branches.

### B8. `in/` and `out/` are open by direct link — known
See the section "Close `in/` and `out/` of work folders from direct links" above.

### B9. A personal model address reads server files — critical (review of 29.09)
- **What.** `voiceHttp()` (`lib/ai/voice.php`) and `aiHttp()` (`lib/ai/deepseek.php`) call the address from personal
  access (`users.access`, account → “AI”) as is: the protocol and host are not checked.
- **Scenario.** Anyone registered (registration is open) sets the “voice address” to `file:///…/secrets.php#` —
  `voice.speak` returns the file contents instead of audio (checked on `readme.md`). The same way — requests
  into the internal network.
- **How to close.** Only `https://`: `CURLOPT_PROTOCOLS` and `CURLOPT_REDIR_PROTOCOLS`; refuse local and internal
  addresses.

### B10. A personal address without a personal key gets the shared key — high
- **What.** `aiAccess()` (`lib/ai/access.php`) lays personal fields over shared ones one by one: a personal
  `ai_api_url` or `voice_api_url` with an empty personal key goes out with the installation's shared key.
- **Scenario.** A person sets their own address and leaves the key empty — the shared DeepSeek or OpenAI key
  arrives at their server in the `Authorization` header.
- **How to close.** Address and key as a pair: a personal address only with a personal key.

### B11. Voice and play — for guests and without a limit — medium
- `voice.session`, `voice.speak`, `ai.play` let a guest of an open project in and spend the shared keys.
- The assistant's daily limit (`aiSpent()`) counts `ai_jobs` through `ai_chats`: delete the chats and the count
  resets; `ai.play` calls the model without a job and is not counted.

### B12. A worker can forge a decision line — low
- `run.event` is open to the worker role: an event of kind `decide` gets into the “decision N → …” lines of the
  reply to the leader (`goMoveLines()`, `lib/api/simple.php`).
