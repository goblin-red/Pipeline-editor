П1

Ромб с числами считает код, а не ИИ

Быстро · важно
Сейчас

В прогоне leader движок нарочно не считает формулу ромба: любое условие, даже a > 13, уходит к Jev. Причина в коде — «ответ worker бывает свободным текстом, формула ошибётся молча».

Итог: ИИ сравнивает числа, на это тратятся время и деньги, есть риск ошибки. А при выключенном Jev каждый ромб ждёт leader.

Предлагаю

Порядок решения ромба:

  • ответ worker совпал с образцом блока (a=<число> b=<число>) — числа берутся строго по образцу, формулу считает код, мгновенно и всегда одинаково;
  • не совпал или условие словами («текст про кошек?») — спрашиваем Jev, как сейчас;
  • Jev не уверен или выключен — решает leader, как сейчас.

Образец ответа уже есть у блоков — это готовый договор, по нему «свободный текст» не собьёт счёт.

Когда код не считает — ромб сразу идёт к Jev, а потом к leader, ничего не угадывая:

  • ответ не совпал с образцом (другие слова, лишний текст, нет адреса);
  • в ответе нет переменной, которая есть в условии (a есть, b нет);
  • два входа ромба дали разные значения одной переменной;
  • число записано не числом («двенадцать», «12–13»).

Образец ответа — не полная схема данных: код берёт только то, что разобрано однозначно. Отсутствие числа никогда не превращается в «нет».

Что дастРомбы с числами — без ИИ и без ошибоки без ошибок счёта. Выполняется правило 9 из progon.md. Прогон работает и при выключенном Jev — для ромбов с числами.
ЦенаРазбор ответа по образцу — одна небольшая функция. Вычислитель формул condEval в движке уже есть.
Где в коде
  • lib/engine/advance.php:383 — для прогона leader формула пропускается
  • lib/api/simple.php:837 — числа из ответов в прогоне leader не разбираются
  • схема 10631: у ромба 37 cond = a > 13, у блока 36 answer = a=<число> b=<число>
П2

«Готово» сразу отдаёт следующее задание

Быстро · важно
Сейчас

Круг leader на каждый блок — два запроса:

  • done — сервер отвечает «СЛЕДУЮЩИЙ: блок 36, возьми op=task&block=36»;
  • task — сервер отвечает «задание в файле …».

Отсюда отдельное правило в инструкции: «не склеивай команды». В r13 — 16 запросов на 7 блоков.

Предлагаю

Если после done (и после begin) выдан следующий блок, сервер сразу пишет его задание в файл и отвечает:

ok: блок 35 принят
задание в файле …/36.1.txt

leader пересылает эту строку worker — и всё. task остаётся для повторного получения и параллельных веток.

Открылось сразу несколько блоков (параллельные ветки) — в ответе по строке «задание в файле …» на каждый. Повторный task отдаёт тот же файл, ничего не выдавая заново.

Что дастВдвое меньше ходов leader: в r13 было бы 9 запросов вместо 16. Правило «не склеивай» больше не нужно. Весь прогон быстрее не вдвое: время worker и доставки сообщений не меняется — сокращаются только ходы leader.
ЦенаНебольшая правка goDone/goBegin плюс строчки в leader.md.
П3

Сторож только смотрит

Быстро
Сейчас

Сторож раз в 30 секунд спрашивает op=where&short=1. Но where не просто читает — он двигает прогон: выдаёт готовые блоки и может позвать Jev. Выходит, фоновый сторож тихо делает ходы за leader, хотя в его описании написано «ничего не пишет в прогон».

Предлагаю

Короткий статус (where&short=1) — только чтение. Двигают прогон лишь команды leader: begin, done, fail, again и полный where.

Простое правило: «спросил — ничего не изменилось; приказал — изменилось».

П4

Старт с выбранного блока и уборка мелочей

Быстро
Сейчас
  • begin отказывает схеме с двумя входами: «простой путь ведёт схемы с одним входом».
  • В полном API выбор входа (from) проверяется, но никуда не сохраняется — выдаются все входы сразу.
  • Команда work дублирует task: блок и так загорается «в работе», когда берут задание.
  • В пакете полного API папка результатов — out/, а у прогона — out/rN/.
Предлагаю
  • begin&from=N — начать с нужного входа; без него при одном входе — как сейчас.
  • Выбранный вход проверяет предпроверка: если с него схема упрётся в слияние, которое ждёт ветку от другого входа, — begin отказывает и называет это слияние. Иначе прогон встал бы тупиком на середине.
  • work убрать из списка команд (оставить тихим синонимом, чтобы старые leader не падали).
  • Ошибки полного API с from и out/ снимаются сами на этапе 2 (П5).
  • Ошибки полного API с from и out/ починить сразу: архивация их не исправила бы, а большую чистку П5 откладываем. run.start сохраняет выбранный вход и выдаёт только его; пакет задания называет папку out/rN/.
Что дастСхемы с несколькими входами можно гонять простым путём. На одну лишнюю команду меньше. Полный API перестаёт выдавать лишние входы и путать папку результатов.
ЦенаНесколько строк в goStartRun.Больше, чем казалось: goStartRun, проверка входа в предпроверке, починка run.start (lib/engine/runs.php:89) и stepPackage (lib/engine/package.php:32), проверка на схеме с двумя входами и слиянием.

П5

Логика — в движке, а не в «простом пути»

Сейчас

simple.php — это 1 286 строк, и это не «разбор запроса и печать ответа». В нём живут свои правила: сборка задания и входа, поиск причины застоя, решение, что показать leader, ловля файлов из ответа, заведение прогона. Параллельно в движке лежит вторая сборка задания (stepPackage) с другими полями.

Сборка задания — одна, её текст видит worker.

Не одним большим переносом, а по кусочку: правим место для конкретной задачи (например, П1 — разбор ответа по образцу, П2 — выдача задания в done) — его логику сразу кладём в lib/engine/. Остальное ждёт своей задачи.

П7

Без таблицы режимов «водитель × судья × Jev»

Чистота
Сейчас

У прогона три настройки: кто ведёт (manual / utility / lead), кто принимает (human / formal), как участвует Jev (off / advisor / judge) — 18 сочетаний.

Простой путь всегда ставит одно: lead + human + judge. Причём «принимает человек» здесь неправда — принимает leader. Код сверяется с режимом в 36 местах.

Предлагаю

Один способ прогона — leader. Остаётся одна настоящая настройка у папки:

Режимы полного API не трогаем: формальная проверка сдачи (formal) может понадобиться будущему ревизору результатов. Меняем только прогон leader:

  • он честно записывает «принимает leader», а не «человек»;
  • у папки появляется галочка:

«Словесные ромбы решает Jev» — вкл/выкл (по умолчанию вкл). Выключено — такие ромбы решает leader.

Остальное поведение задают свойства блоков (образец ответа, лимит кругов, платные вызовы) — как сейчас.

Что дастНет сочетаний, которые никто не проверял. Правило «при выключенном Jev прогон полностью рабочий» соблюдается явно. Журнал прогона правдиво говорит, кто принял работу.
ЦенаСтарые прогоны в базе не трогаем — их поля просто читаются как история. Таблица из 18 сочетаний остаётся — упрощать её будем, только если дойдём до П5.

П10

Шлюз — вызов другой схемы

Гибкость · меняет правило 7
Сейчас

Шлюз только отмечает переход: leader пишет done, и всё. Схему из другой папки нельзя использовать как готовый кусок — её приходится копировать. Правило 7 в progon.md: «шлюз не запускает дочерний прогон».

Предлагаю

Отдельный большой проект со своим планом. До кода нужны правила: как подсхема возвращается при ошибке внутри неё; что будет, если её вызывают второй раз (в цикле или из двух шлюзов); как остановить прогон, когда он внутри подсхемы; где хранятся её результаты и файлы.

П12

Несколько worker — по карточке блока в любой среде

Гибкость
Сейчас

Карточка агента на блоке что-то значит только в Орке. В SendMessage и у субагентов работает один worker, которого нашёл leader, а имя с карточки даже убрано из подсказки, потому что сбивало.

Предлагаю

Строка задания для leader говорит, кому его отдать, если у блока назначен исполнитель: задание в файле … · исполнитель: «Дизайнер». leader сопоставляет имя с сессией или субагентом своей среды. Не назначен — отдаёт своему worker, как сейчас.

  • Связь имени с исполнителем должна быть однозначной: у карточки агента — точное имя сессии или терминала для каждой среды, а не «похожее».
  • Назначенный исполнитель не найден, найдено несколько или он молчит — leader зовёт человека и ждёт. Отдавать задание другому worker «вместо» нельзя.
