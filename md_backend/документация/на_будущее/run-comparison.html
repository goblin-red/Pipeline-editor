Краткое описание

Один движок, разные пути управления

Сервер уже управляет шагами, жетонами и переходами. Полный API, простой текстовый путь и CLI работают с общей моделью данных.

При этом пути различаются запуском, сборкой задания, приёмкой и решением ромбов. Часть правил зависит от режима ведения.

Краткое описание

Общие команды и явные правила

Сохранить работающую модель шагов и жетонов. Объединить запуск и пакет задания, а правила приёмки и ветвления задавать явно.

Текст, JSON и CLI становятся представлениями общего набора команд. Оптимизация запросов выполняется после измерений.

Точечные исправления действующего механизма

Сохраняем нынешний движок и простой путь begin → task → done. Общий слой команд, новые профили и отдельный планировщик снимаются с текущего предложения: необходимость такой перестройки не доказана.

Ближайший план — исправить выбор входа и каталог результата в полном API, уточнить поведение сторожа. Возврат утилиты и оптимизация запросов остаются отложенными идеями.

01

Запуск и выбор входа

Исправить контракт

Два обработчика запуска

begin проверяет схему и выполняет подготовку. run.start создаёт прогон другим путём. Полная предпроверка внутри него не вызывается.

В тесте r3 передали from=27, но получили оба задания: 27.1 и 28.1.
Подтверждено тестом r3 и кодом.

Один обработчик запуска

Любой способ запуска обращается к одной команде: проверить схему, сохранить выбранный вход и создать прогон. Подготовка файлов получает явный результат и порядок восстановления.

Подробности и сохранение поведения

Выбранный вход сохраняется в прогоне и ограничивает начальную выдачу. Для схемы со стартером сохраняется её единственный вход.

Готово, когда выбор одного входа выдаёт только его, а повтор запуска не создаёт второй активный прогон.

Исправить только выбранный вход

В run.start сохранить и учитывать from при начальной выдаче. Объединение обработчиков запуска исключено из ближайшего плана.

Дефект воспроизведён в полном API. Он не является доказательством неисправности простого пути begin → task → done.

02

Настройки выполнения

Сохранить настройки

Режим ведения влияет на правила

driver=manual / utility / lead определяет не только ведение. Простой begin задаёт lead, human и Jev judge; полный API предлагает другие настройки.

Смена пути управления может изменить смысл исполнения той же схемы.
По коду и двум выполненным прогонам.

Правила задаются явно

Профиль отдельно описывает среду, приёмку и выбор ветки. JSON, текст и CLI передают команды с этим профилем.

Подробности и сохранение поведения

Для старых схем профиль выводится из существующих настроек. Смена формата общения сохраняет выбранные правила.

Готово, когда одинаковый профиль даёт одинаковые переходы через JSON, текст и CLI.

Сохранить существующие настройки

Новые профили приёмки и отдельный слой политик сейчас не вводить. Различия режимов явно описать в документации. Возвращаться к унификации только при конкретной потребности.

03

Задание и выходные файлы

Исправить путь

Две сборки пакета

Полный API использует stepPackage, простой путь — goTaskText / goInputs. Они отдельно собирают представление ТЗ и входов.

В пакете API указан workDir/out, а в простом задании — out/rN.
Различие путей подтверждено пакетами r1 и r2.

Одна структура задания

Общий пакет хранит адрес попытки, ТЗ, фактические входы, материалы, правила и пути. Из него формируются JSON, текст и файл задания.

Подробности и сохранение поведения

Единый вычислитель runOutDir задаёт out/rN. Прежние файлы остаются доступны.

Готово, когда оба представления содержат одинаковые входы и каталог результата.

Исправить путь в пакете полного API

Использовать существующий runOutDir для указания out/rN в stepPackage. Общую структуру задания и перестройку обоих сборщиков пока не вводить.

Простой путь уже указывает каталог отдельного прогона. Исправление касается расхождения полного API.

04

Выполнение агентом

Сохранить основу

worker выполняет конкретную попытку

В полном API есть пропуск, session и получение шага. В простом пути leader передаёт задание, worker возвращает адресованную строку.

Тест: другой session не смог забрать уже занятый шаг. Простой путь отклонил противоречащий ответ на прошлую попытку.
Защита session и старого ответа подтверждена тестами.

Те же роли и способы работы

leader и worker сохраняют обязанности. Адаптеры среды доставляют единый пакет и возвращают исходный результат с точным адресом попытки.

Подробности и сохранение поведения

Сохраняются проверки прав, владения шагом, session и адреса. Для работы обеих ролей в терминале предлагается явная среда local.

Готово, когда новая организация кода сохраняет эти отказы и не меняет ответ worker.

Сохранить действующую работу агентов

Роли, адрес попытки, проверки доступа и session остаются прежними. Новые адаптеры доставки и среда local не входят в ближайший план.

05

Сдача и приёмка

Сделать основание явным

submit и done имеют разный смысл

step.submit сохраняет сдачу через предусмотренные проверки. done означает доверенное решение leader и сразу вызывает принятие.

Успешный done сам по себе не доказывает прохождение формальных проверок.
Различие установлено по коду; формальный возврат проверен в r1.

Общие команды, явная политика

Сдача и решение о приёмке имеют единые внутренние команды. Профиль определяет проверяющего: человек, формальные правила, leader или смысловая оценка.

Подробности и сохранение поведения

Доверенная приёмка leader остаётся доступной. В истории записано, кто принял работу и на каком основании.

Готово, когда неверная арифметика возвращается в formal, а согласованный режим lead сохраняет прежний смысл.

Сохранить смысл submit и done

Описать существующие различия приёмки. Новый общий слой команд и профили приёмки не вводить. Доверенное решение leader не объявлять формальной проверкой.

06

Ромб и Jev

Отделить от транспорта

Одна формула решается по-разному

В r1 условие n < 2 вычислено кодом. В r2 при driver=lead это же условие было отправлено Jev.

Jev реально дал yes и no. Время двух вызовов по журналу — 842 и 621 мс.
Подтверждено двумя прогонами и событиями Jev.

Явное правило выбора ветки

Для ромба выбирается: формула, смысловая оценка, решение человека или согласованная комбинация. Этот выбор не зависит от текстового или JSON-ответа.

Подробности и сохранение поведения

Старым lead-схемам сохраняется смысловой режим. Новым числовым схемам можно явно назначить формулу. Неопределённость остаётся ожиданием решения.

Готово, когда профиль сохраняет ветки, а устаревший ответ Jev по-прежнему отбрасывается.

Необязательное улучшение на будущее

Простые числовые условия можно вычислять кодом, а смысловые оставлять Jev. Это отдельная несрочная идея, а не часть обязательных исправлений.

До внедрения нужны однозначные правила типов, допустимых выражений и ошибок. Текущий режим ромбов сохраняется; утверждать отсутствие риска без этих правил нельзя.

07

Циклы, ветви и слияния

Сохранить модель

Сервер управляет жетонами

run_marks связывает переход с попыткой-источником и попыткой-потребителем. readyList определяет готовность; finishCheck — завершение.

В тесте цикл прошёл две итерации, обе параллельные ветви были выданы, слияние дождалось двух результатов.
Цикл и join=all проверены; остальные варианты описаны по коду.

Те же жетоны, яснее планировщик

Выделить расчёт следующего действия из обработки запросов. На входе — граф, попытки и жетоны; на выходе — выдать, проверить, выбрать ветку, ждать или завершить.

Подробности и сохранение поведения

Сохраняются all/any, обратные стрелки, ограничения попыток, конфликты переменных, тупик и критерии успешного завершения.

Готово, когда одинаковые входные состояния дают те же допустимые переходы, включая ошибки и ожидания.

Сохранить существующую механику графа

Циклы, ветвления, параллельные шаги, слияния и жетоны не перестраивать. Проверенные сценарии остаются ориентиром при будущих точечных изменениях.

08

Повторы и восстановление

Без перестройки

Несколько механизмов защиты

Полный путь использует commandId. Простой путь распознаёт адресованный повтор done. again удаляет попытку после проверки зависимостей и сохраняет событие reset.

stepNextAttempt учитывает события reset: удалённый адрес не выдаётся повторно.
Повторы команд проверены; поведение reset установлено по коду.

Единый контракт повтора

Новые изменяющие команды получают устойчивый ID доставки и явный способ восстановления. Старые обращения работают через адаптер совместимости.

Подробности и сохранение поведения

Сохранить это правило и откат зависимостей. Отдельно предлагается хранить отменённую версию попытки вместо удаления её полной записи.

Готово, когда повтор не создаёт работу, изменённое тело отклоняется, а откат не оставляет недействительные зависимости.

Сохранить существующую защиту повторов

Массовое введение ID доставки и изменение хранения отменённых попыток снимаются с ближайшего плана. Отдельные доработки восстановления рассматривать при воспроизведённом сбое или конкретном новом сценарии.

09

Наблюдение и нагрузка

Уточнить сторожа

Повторные чтения состояния

Ход перечитывает граф, шаги и жетоны после действий. Браузер получает run.state, затем run.paint. Ожидание версии опрашивает БД.

Это потенциальные источники нагрузки. Испытания небольших схем не измеряли предел производительности.
Кандидаты выявлены по коду; ускорение не измерено.

Согласованное чтение и меньше повторов

Переиспользовать неизменившийся граф внутри транзакции, убрать повторные загрузки жетонов. Состояние, события и подсветку собирать согласованно.

Подробности и сохранение поведения

Сохраняются version, курсор событий, журнал, подсветка и пауза показа. Результат оптимизации оценивается по SQL, времени блокировки и задержкам ответа.

Готово после сравнения измерений и подтверждения, что состояния и события совпадают.

Уточнить роль сторожа; запросы пока не менять

where вызывает goMove, поэтому его нельзя описывать как чистое чтение. Сначала согласовать назначение: если продвижение нужно — исправить описание; если нужен пассивный сторож — использовать чтение состояния без продвижения.

Оптимизация SQL и объединение выдачи состояния откладываются. Измеренного узкого места в этом аудите нет. Сведения аудитора о прежних замерах здесь не перепроверялись.

Обязательное сохранение функциональности

Исполнение схемы

Блоки, ромбы, циклы, параллельные ветви, слияния, шлюзы в пределах текущего поведения, ограничения и определение тупика.

Контроль работы

Роли, попытки, возвраты, пауза, остановка, восстановление, формальные проверки, решение человека и Jev, учёт внешних заявок.

Данные и совместимость

Материалы, история, журнал, подсветка, события и старые схемы. Приёмка leader и чтение истории engine1 сохраняются.

Это критерии предлагаемой реализации. Отсутствие потери функциональности потребуется подтвердить испытаниями изменений; схема сравнения сама по себе этого не доказывает.

Порядок внедрения

1. Исправить расхождения

Выбранный вход, единый выходной каталог и общий запуск с проверкой схемы.

2. Упростить устройство

Общий пакет, единые команды, явные правила приёмки и ветвления, совместимость старых путей.

3. Измерить и оптимизировать

Повторные SQL-запросы, время блокировки и получение состояния. Числовой выигрыш пока не установлен.

Новый порядок

  1. Точечно исправить from и out/rN в полном API перед его использованием.
  2. Уточнить назначение сторожа и привести описание или поведение к этому назначению.
  3. Остальную архитектуру сохранить. Числовые ромбы — отдельная несрочная идея; утилита и оптимизация — только при доказанной потребности.

Это уточнение предложения. Код движка данным документом не изменён.

Отдельный блок / утилита Goblin

Можно ли вернуть утилиту к работе?

Заключение: да, через реконструкцию вокруг engine2

Утилиту goblin целесообразно обновить и вернуть как программного диспетчера прогона. В ней уже есть подходящая основа: режим engine2 обращается к серверному run.advance, получает задания, хранит контекст worker и наблюдает события.

Возвращать её в эксплуатацию в нынешнем виде преждевременно. Нужно отделить старый цикл, согласовать пакеты и правила с простым путём, завершить доставку заданий и восстановление после сбоев. Основной ожидаемый выигрыш — меньше механических обращений к ИИ-leader; размер экономии ещё не измерен.

Два разных цикла внутри одной утилиты

Старый drive: читает run.get, рассматривает сдачи, при разрешённом accept-clean вызывает приёмку, локально разбирает условия ромбов и отправляет команды открытия. Здесь часть правил исполнения живёт в клиенте.

drive2: вызывает run.advance, читает события и состояние, продолжает ожидание или возвращает причину остановки. Приёмка, выбор ветки и выдача происходят на сервере. Именно эта граница подходит для новой версии.

cmdDriveRoute выбирает новый путь для конкретного engine2-прогона, но без точного прогона или пропуска leader возвращается к старому drive. Поэтому способность старого режима смотреть весь проект нельзя считать готовым современным диспетчером многих прогонов.

Человек / редактор
        ↓ схема + профиль выполнения
Сервер Goblin: правила, граф, попытки, жетоны, приёмка
        ↕ команды и события
Утилита Goblin: вести → доставить → дождаться → восстановить
        ↕ адаптер доступной среды

Смысловой вопрос → Jev по профилю
Неопределённость / ошибка / ручная приёмка → человек

Утилита берёт на себя механическую координацию: ожидание изменений, доставку точного задания, сбор адресованного ответа, повтор доставки и отчёт. Сервер остаётся источником состояния и правил. Исполнитель по-прежнему выполняет содержательную задачу; код утилиты не заменяет его рассуждение.

Для совместимого простого профиля сохраняются: задание файлом, адрес N.K, приоритет описания над ТЗ, материалы блока, in/ и out/rN/, смысловое решение ромбов через Jev, обращение к человеку при сбое. Числовой профиль из общего предложения остаётся отдельной опцией; он не включается старым схемам автоматически.

Доверенное принятие leader требует особого решения при удалении ИИ-leader из цепочки. В профиле lead можно сохранить явное доверие адресованной сдаче исполнителя, но это не доказательство качества. Где leader раньше оценивал результат по существу, нужна формальная проверка, Jev или человек. Автоматическое «принять всё» нельзя незаметно считать эквивалентом такого leader.

Минимальная новая версия

  1. Контракт. Единый пакет и профиль сервера; точные run/step/session, чистый JSON и outcome. Убрать неявный переход в старый drive из нового режима.
  2. Один прогон. Современный drive2 и worker через step.take/submit с устойчивыми ID команд. Состояние исполнения остаётся на сервере; локально хранятся только контекст доступа, курсор и неподтверждённая доставка.
  3. Один реальный адаптер запуска. Сначала поддерживаемый локальный CLI либо конкретная доступная среда. Контроль старта, подтверждение получения, остановка и восстановление. Нельзя считать печать сообщения успешной доставкой.
  4. Несколько прогонов. Ограничить число процессов и внешних вызовов, дать справедливую очередь между прогонами. Один ожидающий ответа run не должен блокировать обслуживание остальных.
  5. Дополнительные среды и legacy. Подключать по одному адаптеру, сохраняя прежние команды совместимыми. Старый engine1 изолировать, удаление не входит в предложение.

Ожидаемая польза и ограничения

Основная польза — убрать лишние обращения к ИИ ради пересылки задания, ожидания и передачи ответа. Это особенно заметно при большом числе коротких шагов. Долгую генерацию изображения, работу внешнего сервиса или рассуждение worker утилита сама по себе не ускорит.

Измерять следует количество обращений и токенов ИИ-leader, время от issued до получения задания, задержку между сдачей и следующим шагом, количество дублирующих запусков, восстановление после обрыва и SQL-нагрузку. Текущие материалы не дают оснований обещать процент экономии.

Заключение

Да, утилите стоит дать вторую жизнь. Наиболее перспективна реконструкция вокруг engine2: сохранить полезный клиентский код, выделить диспетчер доставки и использовать общий серверный контракт. Полная перепись с нуля по результатам анализа не обоснована.

Возврат целесообразен поэтапно: сначала один прогон и один реальный способ запуска, затем восстановление и несколько прогонов. Простой путь leader сохраняется как поддерживаемый вариант. Старую утилиту до реализации и приёмки новой схемы не следует объявлять готовым решением для высокой нагрузки.

Предложение связано с общей оптимизацией прогона. Для возврата в эксплуатацию понадобятся отдельно согласованные испытания CLI: полный проход, возврат, отказ доступа, прерванный запуск, повтор submit, истечение session и перезапуск диспетчера. Эти испытания в данном анализе не выполнялись.
